## 3. Challenge (relevant lenses)

### 3.1 Adoption-mechanics lens (the primary challenge)
- **Hypothesis:** The described evidence (research + partners + docs + frameworks) does **not** identify the adoption bottleneck. A DevRel-in-a-box without a diagnosed bottleneck is broadcast, which Phase 08 lists as a top failure mode.
- **Recommendation:** Make bottleneck-discovery a first-class function of the pack. Each audience pack carries a **friction-log template** and a **funnel-instrumented call-to-action** so the first wave of talks returns structured evidence, not just attendance.

### 3.2 Interoperability / Baseline / "why the web" lens
- **Fact:** Only a **signal** of other-engine movement exists.
- **Hypothesis:** If the pack leads with "ship it today" without Baseline/interop disclosure, GDEs and meetup hosts in other-engine-dominant communities will surface the gap — damaging credibility.
- **Recommendation:** Every pack includes a versioned "Where it works today" panel (Chrome version, other-engine status, Baseline path, polyfill/fallback). Progressive-enhancement guidance is mandatory.

### 3.3 Partner-evidence honesty lens
- **Commitment:** Two public partner statements exist. **Unknown** whether trial/ship/production or whether consented for citation.
- **Contradiction risk (watch):** Promoting a *trial* commitment to a *case study* without consent and verified production deployment violates the skill's "never promote evidence" rule.
- **Recommendation:** Hold partner mentions in the pack at the *verified* stage only. Build the case-study template but ship it empty pending classification + consent.

### 3.4 Claim-accuracy / narrative lens
- **Recommendation:** Single source of truth = a **claims sheet** mapping every public assertion → cited evidence + retrieval date. All three audience packs inherit from it; no pack may contain an uncited claim.

### 3.5 User-impact & review-rehearsal lens
- **Unknown:** End-user impact, a11y, privacy/security/abuse, performance/resource cost.
- **Recommendation:** Before broad GDE/meetup amplification, run a lightweight **pre-review perspective brief** (`user-impact-and-review-rehearsal.md`) so GDEs aren't the ones discovering a privacy or a11y gap on stage.

### 3.6 Launch-resilience lens
- **Unknown:** Whether any contentious dimension exists.
- **Recommendation:** A 10-minute risk-trigger check. If none, document that decision. If any, stand up `launch-resilience.md` before enabling the GDE/meetup channels (these channels amplify fastest and are hardest to recall).

### 3.7 Framework/tool vs. content multiplier lens
- **Hypothesis:** For many adoption bottlenecks, an adapter, CLI diagnostic, or upstream framework contribution scales better than more talks.
- **Recommendation:** The pack's "multipliers" section names the highest-leverage non-content option per segment; content is not the default answer.

### 5.1 Shared core (single source of truth — all three packs inherit)

**A. Claims sheet (mandatory, blocks all packs)**
Table mapping every public assertion → cited source + retrieval date, labeled fact/signal/commitment/hypothesis/unknown. Any claim without a citation is removed. Marked "no claim without a source."

**B. Messaging framework**
- Problem (1 sentence) — tied to the *specific* researched job, [cite].
- Evidence (research + partner stage + framework fit) — each labeled.
- How it works (public-safe, 3 bullets).
- Integration (frameworks/build/server requirements) — [cite framework tests].
- Where it works today (Chrome version; other-engine status = **signal**; Baseline path; fallback) — honest disclosure panel.
- Adoption path / CTA (funnel-instrumented).

**C. Demo registry**
Reproducible environments per framework, with a hosted fallback URL + recorded video for hosts who can't run live. Each demo lists what it does *and does not* prove (e.g., "demonstrates API ergonomics on desktop Chrome; does not prove low-end-device performance").

**D. Friction-log template (reproducible)**
Clean setup → realistic integration, fields: environment, framework, step, expected, actual, severity, owner. Returned by every talk (staff/GDE/meetup) — this is the bottleneck-discovery engine.

**E. Known-limitations & disclosure sheet**
Interop/Baseline, device tiers, a11y status, server/enterprise constraints, any "Chrome-only period" — disclosed in every variant.

**F. Issue-routing & support path**
Where developers report problems, who triages, SLA expectation. (Owner: Support lead — config.)

**G. Owner map / who to ping**
Per workstream owner with escalation point (config per `governance-and-roles.md`).
