# 3. Challenge — Lens A: User impact & review rehearsal

*(All review items below are `pre-review hypothesis`, never `approved`.)*

## 3.1 Three-group benefit/cost (who gets what, who pays)

| Group | Benefit | Cost borne |
|---|---|---|
| **End users** | Possible: faster, offline-capable features; data doesn't leave device *for inference* (if designed so) | Bandwidth (multi-GB), storage, memory, CPU/GPU/NPU, battery, thermal, device lifespan, data-plan money on metered networks; low-end devices may be priced out; possible fingerprinting via model presence/version |
| **Developers / site operators** | No inference server bill; no model ops; simpler integration | Loss of control over model quality, version, availability, update cadence; dependency on browser-supplied model; must build fallbacks for unsupported/low-spec devices; support burden for inconsistent behavior |
| **Implementers / intermediaries** | (Chrome) ecosystem pull, AI-platform positioning | (Other browsers) must implement a substitutable path or be non-conformant; (model providers) face a gatekeeper dynamic; (enterprises) must policy/control unscheduled multi-GB downloads |

**Key DevRel point:** "Zero-cost" describes a transfer — the site operator's cloud inference bill is redistributed onto the end user's device. A cost that moves is not a cost that vanishes. The honest, defensible value proposition is **"cost and data locality shift to the user's device,"** which is genuinely attractive *for some developers and some users* and is *not* the same claim as "zero-cost" or "free."

## 3.2 User-cost and control ledger (must be measured; placeholders for the team to fill)

Every row needs: measurement method, device/config, denominator, uncertainty.

- **Download:** size, timing, frequency; automatic vs user-initiated vs page-triggered vs admin-controlled. *Unknown.*
- **Storage:** persistent footprint; eviction behavior; re-download triggers (update, cache clear, profile reset, device switch). *Unknown.*
- **Compute/battery/thermal:** inference latency, sustained vs burst, GPU/NPU contention, fan/thermal throttle, energy and environmental cost. *Unknown.*
- **Network conditions:** metered networks, data caps, satellite/low-bandwidth, Global South median devices. *Unknown.*
- **Consent/control:** can the user refuse, revoke, delete, see what was downloaded, prevent background download, set a cap? *Unknown.*
- **Trigger surface:** can merely visiting a page cause download or compute? (Worst case for abuse and for "zero-cost.") *Unknown.*
- **Data egress:** anything leaving the device beyond the model artifact fetch (telemetry, catalog selection, crash/safety reporting, model warm-up pings)? *Unknown — this single row decides "private."*
- **Fingerprinting:** can a site detect model presence/version/capability or use outputs to fingerprint? *Unknown.*
- **Accessibility:** model quality across languages, dialects, sign, cognitive load, motion, captions; AT compatibility of any UI surfaced. *Unknown.*
- **Failure/fallback:** unsupported device, out-of-storage, OOM kill, mid-inference abort, version skew, provider/model change. *Unknown.*
- **Reversibility:** can the user get storage back without breaking sites? *Unknown.*

## 3.3 Pre-review perspective matrix (each = `pre-review hypothesis`)

**Accessibility.** On-device models frequently underperform cloud models for non-dominant languages, dialects, accents, and disability-adjacent tasks. If the API pushes developers toward a lower-quality local model for, e.g., captioning or text simplification, **the accessibility floor can drop** even as privacy improves. Fallback must preserve the *task*, not merely avoid a crash.
*Hypothesis:* reviewers will ask for measured quality parity across locales/disabilities vs the cloud baseline, and for a developer-facing quality signal so sites don't silently degrade AT users.

**Privacy & data protection.** "Private" is a whole-system property; inference location is one input.
*Likely reviewer questions:* What data leaves the device, to whom, for what purpose, retained how long? Is it minimized, purpose-limited, controllable, deletable? Does model *download/selection* reveal anything about the page/user (a content-driven catalog choice is a leak)? Is "local/private" **demonstrably** bounded — i.e., is there a measurement showing the egress surface? What's the fingerprinting surface from model presence/version/outputs? What about hostile use at scale?
*Pre-review hypothesis:* "Private" survives only if paired with (a) a stated, minimal egress list, (b) user control, (c) a demonstrable test of "nothing but X leaves the device," and (d) a fingerprinting analysis.

**Security & abuse.** A page that can trigger multi-GB download + sustained local compute is a resource-exhaustion / battery-drain vector. Hostile sites could probe model outputs to infer attributes about user-supplied or scraped media.
*Pre-review hypothesis:* reviewers will want origin gating, quotas/rate limits, user-visible resource controls, background-use rules, and an abuse model — before the ergonomics claim "easy for developers" becomes "easy for attackers."

**Standards & interoperability.** Can the API be independently implemented? The hard standards question is the *model*: if the browser supplies and updates one model, conformance is "implement this behavior" *and* "ship a compatible model," which is unusually heavy. Other engines may accept the API but not the model choice.
*Pre-review hypothesis:* TAG/interop reviewers will probe (a) independent implementability including model substitutability, (b) the Baseline path, and (c) the cost of a Chrome-only period that includes a Chrome-only model.

**Legal, regulatory & competition.** These are *questions for qualified reviewers*, not legal conclusions. The browser becoming the model distributor/provider touches: defaults/bundling/self-preferencing; whether independent providers can offer a genuinely substitutable model path; whether the browser controls quality levels, terms, and updates devs can access; and data-protection duties for anything that does egress. Different jurisdictions (competition, consumer protection, data protection) may each have a question.
*Pre-review hypothesis:* competition reviewers will focus on the model-selection/gatekeeper angle; the team should go in with an answer to "can a third-party model provider reach these developers and users on equal terms?"

**Engineering, performance & operations.** Worst-case device cost; update/version skew across the fleet; partial rollout where some profiles have the model and some don't; corrupted/abandoned model state; rollback. *Unknown — needs ops plan.*

**Enterprise & administrators.** Unscheduled multi-GB downloads are an IT problem: bandwidth budgets (branches, EDU, shared kiosks), storage quotas, audit, policy to disable/delay/cap, and migration. *Pre-review hypothesis:* enterprise reviewers will want group policy/MDM controls and notice early enough to act.

## 3.4 Public-question / analogous-coverage brief

Recurring critique patterns from analogous browser launches (these are *patterns to anticipate*, not attributed quotes; treat each as requiring current source retrieval before launch):

1. **"Helpful" background downloads that cost users.** Features that fetch large artifacts without crisp consent get criticized for bandwidth/storage/battery costs — especially on metered networks and low-end hardware. *Likely press/civil-society question:* "Who asked for this download, when, and can I stop it?"
2. **"Private" claims by large platforms.** On-device/"private" AI claims receive sustained scrutiny over what egress and telemetry actually exist; the gap between "local" and "private" is the standard attack surface. *Likely question:* "Private from whom, exactly, and what's the proof?"
3. **Browser bundling a service/capability.** Competition and civil-society scrutiny of defaults, gatekeeping, and whether independent providers can compete on equal terms. *Likable question:* "Can anyone else's model run here?"

For each: the right response is **evidence, narrower claims, controls, or an accepted-and-stated tradeoff** — never spin. The team can be well-prepared for all three *if it narrows the claims now.*
