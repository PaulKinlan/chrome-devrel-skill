### 4.4 The four cluster playbooks (tactics matched to the bottleneck)

#### Playbook A — No demo
- **Bottleneck:** developers cannot see/try/understand; evidence collection blocked.
- **Steps:** (1) classify the demo's job — discovery, first-success, or realistic integration; (2) build the **minimal** demo that exercises the *realistic* path, not the happy path; (3) pair it with a **friction-log-informed sample** that documents setup, fallback, and known limitations; (4) add the demo to the manifest's `artifacts.demo` with version + owner + last-tested environment.
- **Stage gating (advisory):** incubation → minimal example is acceptable; ship (phase 6) → missing demo/sample is a **blocker** for the launch brief.
- **Artifact:** Demo & sample plan (per `artifact-templates.md`), each carrying metadata, sources, audience, owner, status, unresolved assumptions, review requirements.

#### Playbook B — Stale docs
- **Bottleneck:** canonical source of truth has diverged from implementation or lost an owner.
- **Steps:** (1) run a **documentation gap analysis** (required-docs table: reference/quickstart/sample/FAQ/known-limitations, each with status/owner/gap); (2) diff docs vs current spec/explainer vs implementation — **a mismatch is a finding**; (3) assign a refresh owner and an SLA by stage; (4) wire the freshness monitor (§4.3) so staleness recurs, it alerts.
- **Anti-pattern to avoid:** rewriting the docs to match a quirk of implementation without checking whether the *spec* is wrong.
- **Artifact:** Documentation gap analysis + freshness SLA table.

#### Playbook C — Unresolved negative positions
- **Bottleneck:** interoperability/legitimacy; risk of a Chrome-only period masquerading as a web standard.
- **Steps (per `stakeholder-critique.md`):** (1) state the power/capability change; (2) discover affected constituencies (broad, then retain only material ones); (3) build a **dated source packet** — for each: URL, publisher, publication + retrieval date, quotation, evidence class (**recorded position** / **principle-grounded inference** / **open question**); (4) steelman the strongest concern, don't pick weak objections; (5) produce the critique matrix (constituency, evidence class, source, strongest concern, severity vs likelihood, current response, gap, next action, owner/timing, status); (6) red-team the announcement; (7) set redesign/narrow/another-trial/delay/rollback/abandon triggers.
- **Hard rules:** no support inferred from silence (A5); no personal-opinion/organisation conflation; a mitigation is not resolution until evidence shows it works.
- **Escalation:** unresolved material negative position → human decision (API Owner / standards liaison / product), **not** a DevRel call to ship or not.
- **Artifact:** Critique matrix + dated source packet per feature.

#### Playbook D — Strong adoption + recurring framework failures
- **Bottleneck:** product/framework/server integration, not awareness. (The named support-phase failure mode.)
- **Steps (per `friction-log.md` + `phases/08-09`):** (1) **verify the adoption denominator first** — exact counter vs family counter; if family-level, label scope explicitly (A3); (2) run a reproducible friction log across representative framework/library × server × device × engine configurations; (3) build an **issue taxonomy** with stable IDs, reproductions, environments, severity, workaround cost, owner, status; (4) classify root cause — product/spec/compat/framework/server/tooling/docs/messaging; (5) add **immutable regression/conformance assertions** where behavior is testable; (6) contribute upstream where that scales better than content; (7) feed learnings back to product/docs/spec; (8) report exact **tested/total/fixed/remaining/blocked** counts.

## 7. Escalation, residual risks, and required human decisions

Per `continuous-loop.md` stopping/escalation rules, the loop **escalates** (does not self-decide) when:

- **Blocker:** a product concern needs redesign, narrowing, delay, rollback, or abandonment (e.g., a Cluster-C position that no mitigation addresses).
- **Blocker:** formal review or qualified advice is required (privacy/security/a11y/legal/API Owner) — DevRel routes, never concludes.
- **Blocker:** evidence conflicts materially across sources and the denominator is too unstable to support the claim.
- **Blocker:** a harassment/privacy/security/safety incident occurs → launch-resilience + HR path; aggregate-only reporting; never make an individual absorb abuse.
- **Blocker:** monitoring would cross a privacy or organizational boundary.
- **Unknown** that cannot be resolved from public sources and requires partner/internal input.
