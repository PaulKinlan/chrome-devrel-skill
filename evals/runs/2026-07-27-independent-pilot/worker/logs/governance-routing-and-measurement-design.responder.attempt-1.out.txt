## 4. Challenge (relevant lenses only)

**Lens: the request's premise (stakeholder critique).** **[contradiction]** Two things are being bundled — a launch gate and a success metric — and both lean on evidence that doesn't yet exist (no partners, no cross-engine positions, no privacy review). **[recommendation]** Decouple them: ship-readiness is decided by the team's canonical process; DevRel owns the *evidence quality* and *adoption/measurement* track. Keep these as two separate workstreams with separate exit criteria.

**Lens: measurement framing.** **[contradiction]** "One adoption metric that proves it was successful" conflicts with the measurement principle "avoid one universal score." Single success metrics reliably do one of: get gamed, measure the wrong denominator, or claim success by isolating a flattering slice. **[recommendation]** Replace "one proof metric" with a small, coherent set: one **primary adoption indicator** + **guardrails** that catch the ways a single number can lie + one **learning metric**.

**Lens: end-user & review rehearsal.** **[unknown]** Privacy review is the most acute gap because it is a formal-review-if-required dimension and it is at zero. **[recommendation]** Route privacy first; it is on the critical path for *any* milestone ship, not just DevRel's comfort. Do not treat "no privacy review" as a soft gap.

**Lens: interoperability.** **[unknown]** Cross-engine silence is being implicitly carried as neutral. **[recommendation]** Reach WebKit/Gecko (and TAG if relevant) for a position *before* ship messaging is written, so the launch brief can state interop status honestly rather than be corrected later.

**Lens: problem/use-case validity.** **[unknown]** We are being asked to bless adoption of a feature whose developer problem is unstated. **[recommendation]** Re-ground in one sentence of problem + one attributable developer need before defining the metric, because the metric's denominator depends on the segment.

**Lens: launch resilience / team safety.** **[unknown]** If the feature touches consent, identity, payments, or any politically charged surface, absence of a plan is itself a risk. **[recommendation]** A 1-question triage: "Could this become a contentious or targeted launch?" If yes, stand up the launch-resilience pack before ship, not after.

For every material gap, the resolution is concrete (research, interview, partner outreach, privacy routing, friction run, demo, measurement) and sequenced in Section 6.

#### Why not one metric

**[fact]** The measurement framework's own rule is "avoid one universal score; different objectives need different metrics," and every metric must state denominator, limitations, and privacy boundary. A single "adoption %" can be true while the feature is failing on interop, sentiment, or correctness. So the plan below gives **one primary** plus **guardrails**.

#### Primary adoption indicator (proposed; selection pending)

**Recommendation: verified production deployment evidence** as the primary — because for an API, the most falsifiable "did it work" signal is a named partner shipping it in production, and counter percentage does not isolate the feature.

```yaml
metricId: adopt-prod-deployment
name: Verified production deployments of <feature>
objective: Did real developers ship this in production, not just try it
metric: Count of named partners/sites with consented, attributable evidence of production use
denominator: _config-required: target partner segment definition (e.g., top-N by traffic, or named vertical)_
baseline: 0 (current — no partner commitments on record)
target: _config-required — set AFTER the partner pipeline exists; do not pick a number to satisfy the milestone_
window: 0/30/90/180 days post default-availability
instrumentation: _config-required — partner feedback loop + opt-in case-study process + public usage signals (with consent)_
privacyBoundary: _config-required — partner-attribution consent; no end-user personal data for this metric_
scope: Production use of this specific API shape; excludes demos, docs samples, and Origin-Trial-only use
confidence: _low until ≥1 attributable production deployment exists_
owner: DevRel practitioner of record
cadence: milestone + 30/90/180-day checkpoints
threshold: _config-required — define the value that means "broad enough to declare adoption," separately from the launch decision_
limitations: Self-selection bias; count ≠ prevalence; a small number of high-profile deployments can mask low long-tail adoption
```

**[recommendation]** Note the embedded signal: a primary metric whose **baseline is 0 partners** *is* the readiness gap. Picking this metric makes the pre-ship evidence hole visible rather than papering over it with counter movement.

**Fallback primary (if production-deployment evidence is too slow for the milestone):** ChromeStatus usage-counter percentage over measured Chrome page loads — **with the explicit limitation stated in the framework**: family counters don't isolate the feature, "no counter" = unknown not zero, and this measures *Chrome* adoption only, not web-platform success. Acceptable as a milestone checkpoint signal, **not** as proof of success.

#### Guardrails (these are what stop the primary number from lying)

```yaml
- metricId: interop-other-engine-status
  name: Other-engine implementation/position status
  objective: Chrome-only is not broad success
  metric: WebKit/Gecko public position + implementation status (dated)
  denominator: Target engines (WebKit, Gecko)
  baseline: _unknown — cross-engine positions not established_
  target: _config-required_
  instrumentation: Public positions, bug trackers, standards venues
  limitations: Position ≠ implementation; silence ≠ opposition
  privacyBoundary: none (public signals)
  owner: Standards/TAG liaison
  cadence: pre-ship + 90/180-day
  threshold: _config-required_

- metricId: dev-sentiment-trend
  name: Developer sentiment trend (this API)
  objective: Catch negative feedback and design issues early
  metric: Sentiment on attributable feedback about *this API shape*
  denominator: Representative developer sample
  baseline: _config-required_
  target: non-declining sentiment
  instrumentation: survey + issue-tracker/forum themes
  limitations: selection bias; self-report; volume ≠ prevalence
  privacyBoundary: _config-required_
  owner: DevRel practitioner of record
  cadence: 30/90-day
  threshold: _config-required — e.g., emergence of recurring correctness/ergonomics complaint themes_

- metricId: friction-items-ship-blocker
  name: Unresolved friction items at ship
  objective: Known-integration problems should not cross the ship line unflagged
  metric: Count/severity of open friction-log items
  denominator: Total friction items logged
  baseline: _config-required — requires a friction run that has not happened_
  target: zero open severity-high at default-availability
  limitations: survivorship bias on prevented items
  owner: DevRel + engineering TL
  cadence: pre-ship gate + post-ship 30-day
  threshold: any severity-high = escalation
```

#### Learning / co-design metric (so success includes "we built the right thing")

```yaml
- metricId: codesign-influence
  name: Design changes influenced by developer evidence
  objective: Evidence that the shipped shape reflects real developer need, not just "shipped on time"
  metric: Tagged design changes traceable to attributable developer evidence
  denominator: Total design decisions in scope
  baseline: _config-required_
  target: _config-required_
  instrumentation: issue-tracker tags linking decisions to evidence
  limitations: attribution is subjective
  owner: DevRel practitioner of record
  cadence: milestone
  threshold: _n/a (directional)_
```

- Any baseline/target number (these are **config-required**, and inventing them would be fabricating metrics).
- A claim that counter movement = success.

## 6. Plan (stage-appropriate; evidence state Phase 03–04, intent Phase 06)

**Outcome & exit criteria.** Convert the readiness matrix from mostly-Unknown to *rated-with-linked-evidence*, and give the actual decision-makers (API Owner, privacy, security, a11y, release) a complete ledger — **not** a DevRel approval.

**Blockers (explicit).**
- **[blocker]** Privacy review not routed. On the critical path for milestone ship.
- **[blocker]** Cross-engine positions unknown; cannot write honest interop messaging without them.
- **[blocker]** No partner pipeline; the primary adoption metric has baseline 0 and no path to a non-arbitrary target.

**Suggested sequence.**
1. **Re-scope the ask (days).** Send the governance-boundary reply in Section 2. Split "launch gate" (canonical process) from "evidence + adoption + measurement" (DevRel).
2. **Route the formal-review dimensions (this week).** Privacy first; security and a11y per the team's canonical process. *DevRel flags and routes; it does not determine sufficiency.*
3. **Cross-engine + standards outreach (parallel).** Request dated WebKit/Gecko positions; record silence explicitly as "no position," not "support."
4. **Re-ground the problem (this week).** One-sentence problem + target segment + one attributable developer need at the API-shape level. This unblocks the metric denominators.
5. **Stand up the partner pipeline (2–4 weeks).** Move the strongest "interest" signals from interest → active evaluation → **trial commitment** (with permission to attribute). Even one trial commitment changes the readiness picture materially.
6. **Friction + ergonomics run (1–2 weeks).** Clean setup through realistic integration, mobile + desktop, a framework, a server constraint.
7. **Finalize measurement selection + config (parallel with 5–6).** Lock the primary + guardrails; fill baselines/targets only *after* the partner pipeline and segment exist.
8. **Launch-resilience triage (this week, 1 question).** Could this become contentious/targeted? If yes → stand up the resilience pack before ship.
9. **Evidence ledger → transition packet (Phase 06).** Only when the matrix is rated-with-evidence do we produce the prepare-to-ship transition packet (claim ledger, review-state matrix, docs/demos, support/rollback, monitoring).

**Risks if shipped next milestone as-is.** **[hypothesis]** unreviewed privacy surface discovered post-ship; Chrome-only numbers presented as success; uncited "interest" claims challenged publicly; engineers left as default responders.
