## 3. Challenge — relevant lenses by cluster

The four clusters map to four lenses. I will not apply all lenses to all features (that is the anti-pattern of an undifferentiated checklist).

### Cluster A — DEMO-GAP (no demos; mostly Incubation/Prototype/Trials)
- **Lens:** Documentation, samples, demos; API ergonomics; problem/use-case validity.
- **Challenge:** A missing demo usually hides a deeper unknown — *what job does the demo prove?* A demo that only shows the happy path is a toy. Before building demos, confirm the **use case is valid and the problem is real**, else the demo manufactures demand that doesn't exist (anti-pattern A4).
- **Themes to resolve:** (1) Is there a concrete developer job? (2) Is the API usable without hidden knowledge? (3) Mobile + desktop coverage?

### Cluster B — DOCS-ROT (stale docs; mostly Adoption/Support)
- **Lens:** Documentation gap analysis; friction log (the doc-vs-impl path).
- **Challenge:** Stale docs are an **evidence-integrity** problem. A doc that disagrees with the shipped implementation misleads developers and reviewers. The friction rule is explicit: a doc/explainer/spec/impl mismatch is a finding **even if one path works**. Each stale doc is a candidate regression assertion.
- **Themes:** (1) Which docs disagree with current impl/spec? (2) Are samples still reproducible on current stable? (3) Are known-limitations still accurate?

### Cluster C — POS-OPEN (unresolved negative positions; Incubation/Wide Review)
- **Lens:** Interoperability & compatibility; stakeholder critique; standards positioning.
- **Challenge:** An unresolved negative position is a **contradiction**, not a Docs problem. Resolving it is rarely "write a better article" — it is design/spec/evidence work, sometimes scope narrowing or parking. Steelman the concern; do not role-play remembered vendor stereotypes. Map each position to: design change / new evidence / scope change / principled disagreement-acknowledged.
- **Themes:** (1) What exactly is objected to (design / privacy / perf / alternatives / interop / process)? (2) What evidence would move it? (3) Is Chrome-only a tolerable interim, and at what interoperability cost?

### Cluster D — FW-FAIL (strong adoption, recurring framework failures; Adoption/Support)
- **Lens:** Evidence-based integration friction (friction-log); ecosystem/framework compatibility; measurement.
- **Challenge:** "Strong adoption + recurring failures" is the **highest-leverage** cluster: real developers are hitting real walls in production stacks. This is exactly where the continuous-loop rule mandates a **real executed friction run now**, not a template. Each recurring failure becomes an immutable regression/conformance assertion so it cannot silently return (anti-pattern: silent regressions across versions).
- **Themes:** (1) Which frameworks/versions/runtimes? (2) Is it a framework bug, a spec ambiguity, or an impl regression? (3) What is the workaround cost paid by developers today?

**Cross-cluster lens — launch resilience:** Unknown whether any of the 40 is contentious or targeted. If any POS-OPEN feature is high-salience, load `modules/launch-resilience.md` before it nears ship. This is a triage question, not an assumption.
