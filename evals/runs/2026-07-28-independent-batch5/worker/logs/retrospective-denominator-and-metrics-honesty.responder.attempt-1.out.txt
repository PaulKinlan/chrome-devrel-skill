## 3. Challenge

### C1 — "Single number of features shipped successfully"

- **Contradiction (anti-pattern A6):** the skill's operating rule is *"never infer success from shipment, usage alone, press sentiment, or missing criticism."* Shipment is a process event; success is a multi-dimensional outcome. A single scalar forces a false collapse.
- **Contradiction (R1):** if the single number is built by summing milestone rows, it overcounts. 355 memberships → 291 features.
- **Hypothesis:** a single success number would mislead downstream decision-makers because it hides that 139 features have no measurable adoption and that outcomes are mixed by dimension.
- **Recommendation:** ship *one shipment count* (clean, honest) plus a *multi-dimensional outcomes view*. Do not label the shipment count as "success."

### C2 — "Mark the 139 unmapped features as zero adoption"

- **Contradiction (R2 / anti-pattern A1):** absence of a public counter means adoption *cannot be measured from public telemetry*, not that adoption is zero. Marking zero fabricates evidence. The validated run explicitly forbids this ("States or implies unmapped features have zero usage").
- **Signal:** the proposal itself suggests the team is under pressure to produce a tidy number. That pressure is the actual problem to address, not the missing counters.
- **Recommendation:** use the canonical phrasing for every unmapped feature: *"No public ChromeStatus counter is mapped; adoption cannot be measured from public telemetry."* Reserve a separate, honestly-labeled bucket for any private/internal adoption signal (and keep it out of public artifacts).

### C3 — Family counters presented as feature adoption

- **Risk (R3 / A3):** 74 of 152 mapped counters are family/property-level. Presenting family usage as feature-specific adoption overclaims.
- **Recommendation:** every counter citation must carry scope labels: exact / family-property / trial-only / multiple / ambiguous, plus "what it measures and what it does not."

### C4 — The OT→GA example (M144 Origin Trial, M148 Enabled by default)

- **Fact:** this is one feature with two milestone memberships. It is counted **once** in any unique-feature denominator.
- **Recommendation:** if you want a "reached GA" view, count by the *Enabled-by-default* membership, still deduplicated by feature ID. Report OT-only features as a distinct category ("in trial, not yet GA") rather than folding them into either "shipped" or "not shipped."

### C5 — What the counter percentage actually means

- **Fact:** ChromeStatus metrics report the share of measured Chrome HTTP/HTTPS page loads on which the counter fired.
- **Recommendation:** never translate that percentage into unique developers, sites, users, successful tasks, satisfaction, or end-user benefit. A missing mapping is "no mapped public counter found," never "no adoption data exists" (internal telemetry may exist).

### 5.1 The denominator (do this, not the single number)

**Unit of analysis = the unique ChromeStatus feature ID.** Always deduplicate by ID before any count.

| Count | Value | What it is | What it is not |
|---|---|---|---|
| Unique features shipped (any form) | **291** | Features with ≥1 launch event in 140–150 (Enabled by default, Origin Trial, etc.) | Not a "success" count; not 355 |
| Milestone memberships | 355 | Feature×milestone rows (non-additive) | **Never** sum these for a feature count |
| Features in 2+ milestones | 41 | e.g., OT@144 + Enabled@148 = 1 feature | Counted once in 291 |
| Reached GA (Enabled by default) | *Report as a subset of 291, dedup'd by ID* | Features whose membership includes "Enabled by default" | OT-only features are a *separate* category, not "not shipped" |
| In Origin Trial only | *Report as a subset of 291* | OT membership, no Enabled-by-default in window | Still "shipped" (in trial); do not fold into GA |

**The only honest single number to give leadership for "how many shipped" is 291** — and it must be labeled *shipped*, not *successfully shipped*.

### 5.2 Metrics approach (adoption is a distribution, not a number)

Reject one adoption score. Report adoption as a **coverage distribution with mandatory scope labels (R3)**:

| Bucket | Count | What you can say |
|---|---|---|
| Exact-feature counter mapped | 10 | "Adoption measured directly." Cite % of measured Chrome page loads. |
| Family/property counter mapped | 74 | "Family-level signal; does not isolate this feature." Cite % with that caveat. |
| Other mapped (trial / multiple / ambiguous) | 152 − 10 − 74 = 68 | Cite with the specific scope label. |
| **No public counter mapped** | **139** | **"No public ChromeStatus counter is mapped; adoption cannot be measured from public telemetry."** Not zero. |

Rules every adoption figure must follow:
- State mapping status (exact / family / trial / multiple / ambiguous / none).
- State what the counter measures and what it does **not** measure.
- State whether the counter isolates the feature or measures a broader family.
- A counter percentage = share of measured Chrome HTTP/HTTPS page loads where it fired. **Never** convert to developers / sites / users / success / satisfaction.
- "No counter" ⇒ unknown. (R2; verified 139/139 in the run.)

### 5.3 Outcome framing (success is multi-dimensional)

Per feature, score each relevant dimension **success / mixed / failure / unscored**, with cited evidence and limitations. The overall status must **not** hide mixed dimensions (no averaging into one grade).

Dimensions (from the retrospective module):
1. Developer problem/value
2. End-user impact and control
3. Adoption and durable production use
4. Interoperability / other-engine / Baseline progress
5. Implementation quality and compatibility
6. Evidence quality and communication accuracy
7. Documentation / demo / integration quality
8. Support burden and issue resolution
9. Team / launch resilience (where public evidence exists)

### 5.4 Dashboard mock (five tiles, no single score)

1. **Shipment** — 291 unique features (355 memberships; 41 multi-milestone). Sub-rows: Reached GA / OT-only.
2. **Adoption evidence coverage** — 10 exact · 74 family · 68 other-mapped · 139 unmapped (= unknown, not zero).
3. **Outcome rollup** — per dimension, the success/mixed/failure/unscored distribution across 291.
4. **Interoperability** — other-engine status distribution (flag the 69 unknown).
5. **Evidence quality** — depth tier (204 ChromeStatus-only · 87 deeper) and risk-trigger coverage (R4).

### 5.5 Forbidden moves (print on the back of the dashboard)

- ❌ Summing milestone memberships as features (A2).
- ❌ Labeling unmapped features "zero adoption" (A1 / R2).
- ❌ Presenting family-counter usage as feature-specific adoption (A3 / R3).
