```yaml

```

**Problem.** Developers building 3D/configurator/AR/spatial/data-viz experiences on the web cannot render **live, interactive, accessibility-preserving HTML** onto a WebGL/WebGPU surface. **[fact]** Today's options are all deficient: `html2canvas`/`dom-to-image` rasterize to a static image (non-live, AT-invisible, expensive, drifts from real state); repainting to a 2D `<canvas>` texture is manual, static, and a11y-invisible; CSS 3D transforms can't join a real scene graph (z-fighting, perf, no true 3D); rebuilding UI in-canvas discards DOM semantics and is costly. **[fact — workaround ecosystem]** Who experiences it: 3D/configurator devs, data-viz/dashboard authors, AR/spatial-UI builders, and — critically — **AT users for whom 3D web content is largely inaccessible today.** **[hypothesis, grounded]**

**Use cases (hypotheses, to validate).**
1. 3D product configurator rendering live pricing/UI on the product surface.
2. Spatial/AR UI where real DOM controls float in 3D and remain AT-accessible.
3. Data-viz with rich HTML chart/label overlays embedded in a 3D scene.
4. Games/interactive experiences with HTML HUDs that stay accessible and live.
5. Accessible 3D educational/exploration tools for AT users.

**Alternatives considered.** Snapshot libraries (static, a11y-lost); canvas repaint (manual, static); CSS 3D (no scene integration); in-canvas rebuild (no semantics); native stacks (Unity/Unreal solve it off-web but aren't the open web). Each fails live, interactive, **or** accessible — frequently all three.

**Non-goals (proposed).** Not a replacement for 2D DOM layout; not a license to render arbitrary cross-origin content without an isolation/permission model; not a substitute for fixing 3D a11y at the scene level where textured HTML isn't the answer.

**Evidence.** Workaround-pain = **[fact, widely documented]**. Demand for *this API shape* = **[unknown]** until cohort research completes. Accessibility benefit = **[hypothesis]** until AT tests (C3) complete.
